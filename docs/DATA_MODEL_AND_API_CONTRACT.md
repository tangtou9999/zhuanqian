# 数据模型与 API 契约（V0.1）

## 1. 架构决策

第一版正式系统采用清晰的模块化单体，不急于拆微服务：

- Web 前端：用户端、运营后台、企业端分开权限与路由。
- API 服务：统一身份认证、权限校验、业务规则和审计。
- PostgreSQL：业务主库，金额全部用整数“分”存储。
- 对象存储：任务附件和交付文件，不把文件二进制塞进数据库。
- 后台队列：通知、文件扫描、超时提醒和报表计算。
- 支付：只接入有资质支付机构的产品；平台不自建资金池。

静态 GitHub Pages 只承载展示原型，不能直接连接数据库或保存真实业务数据。

## 2. 角色与权限

| 角色 | 核心权限 |
|---|---|
| 普通接单者 | 浏览已发布任务、领取、提交成果、查看本人任务和账务 |
| 需求方个人 | 创建自己的需求、确认报价、查看自己订单、验收和申诉 |
| 企业成员 | 按组织角色查看和管理本企业需求与项目 |
| 运营审核 | 审核需求、核验企业、处理任务上下架 |
| 项目运营 | 拆单、分配、跟进进度，不得修改已确认的财务流水 |
| 质检人员 | 查看交付、按验收清单审核、退回修改 |
| 财务人员 | 对账、查看账务、发起经授权的结算流程 |
| 超级管理员 | 角色授权、系统配置、审计；高风险操作双人复核 |

所有接口默认拒绝访问。不能只靠前端隐藏按钮；服务端必须检查当前用户、组织成员关系、资源归属和操作权限。

## 3. 核心业务模型

- demand_requests：需求入口，必须审核后才能转项目或公开招募。
- projects：完整商业订单，区分 platform_managed 自营承包和 marketplace 撮合。
- project_tasks：项目拆出的子任务，定义交付物、报酬、验收规则和返工上限。
- task_assignments：任务与接单者的约定关系，冻结接单时的报酬。
- submissions / reviews：成果版本和审核记录，禁止覆盖旧版本。
- orders / ledger_entries：订单金额和不可随意修改的账务事件。
- order_cost_items：质检、返工、材料、物流、支付等成本。
- file_assets：文件权限、授权元数据和保留期限。
- disputes / audit_logs：争议处理和后台操作审计。

数据库迁移见 [001_initial_schema.sql](../database/migrations/001_initial_schema.sql)。

## 4. API 契约草案

统一前缀 /api/v1，JSON 使用 UTF-8；金额字段统一以整数分传输。每个写接口支持 Idempotency-Key，防止重复提交。

| 方法与路径 | 用途 | 权限 |
|---|---|---|
| GET /tasks | 浏览已发布任务 | 登录用户/访客按策略 |
| GET /tasks/{id} | 查看任务详情与规则 | 已发布任务可见 |
| POST /tasks/{id}/assignments | 领取任务 | 接单者 |
| GET /me/assignments | 查看本人任务 | 接单者本人 |
| POST /assignments/{id}/submissions | 提交成果版本 | 该任务接单者 |
| GET /assignments/{id}/submissions | 查看提交历史 | 任务相关方 |
| POST /submissions/{id}/reviews | 验收或退回修改 | 授权质检人员/需求方 |
| POST /demand-requests | 提交需求 | 个人/企业成员 |
| GET /ops/demand-requests | 获取审核队列 | 运营审核 |
| POST /ops/demand-requests/{id}/decision | 通过、退回或拒绝 | 运营审核 |
| POST /ops/projects | 建立项目订单 | 项目运营 |
| POST /ops/projects/{id}/split | 创建子任务 | 项目运营 |
| POST /ops/tasks/{id}/assign | 指派接单者 | 项目运营 |
| GET /ops/projects/{id}/unit-economics | 查看项目贡献毛利 | 项目运营/财务 |
| POST /disputes | 发起争议 | 订单相关方 |
| GET /me/ledger | 查看本人账务明细 | 本人/财务授权 |

### 关键写接口约束

- 领取任务：事务内检查任务状态、剩余数量、资格和截止时间，再创建 assignment；重复请求返回同一结果。
- 提交成果：创建新 submission 版本并关联文件，不允许覆盖历史版本。
- 验收：必须写入 reviewer、decision、理由和清单结果；拒绝/返工必须给出具体原因。
- 拆单：子任务报酬合计不得超过项目预算，除非有经过授权的预算变更记录。
- 订单确认后：客户价、接单者报酬和服务费率均需版本化；不能静默改价。
- 账务流水：只追加，不更新/删除；更正通过反向或调整流水完成。
- 结算：幂等键、支付机构流水号和对账结果缺一不可。

## 5. 项目利润计算

自营承包项目：

贡献毛利 = 客户合同收入 - 接单者报酬 - 质检成本 - 返工成本 - 材料成本 - 物流成本 - 支付成本 - 退款/坏账准备

撮合项目：

贡献毛利 = 平台明示服务费 - 支付成本 - 审核与客服成本 - 争议/退款成本

不能把项目报价与接单者报酬之间的差额直接当净利润。人工、税费、获客、服务器和管理成本必须在经营报表中另列。

## 6. 真人素材与隐私

真人拍摄任务必须在接单前明确：

- 出镜者、拍摄者与上传者身份关系；
- 肖像、声音、作品版权和场地许可；
- 使用渠道、地域、期限、剪辑和二次创作权限；
- 是否允许广告投放、商业推广或模型训练（默认不授权模型训练）；
- 撤回授权的处理规则与已交付内容的法律边界。

文件上传必须走服务端签发的短期上传凭证；完成病毒扫描和文件类型验证后才能进入审核。下载按项目成员授权，访问有日志，并按约定期限删除。

## 7. 资金与通知

- 不把“待验收”金额记为“可提现”。
- 不在普通数据库中自行托管客户资金；支付、分账和结算方案必须由持牌机构提供并经过法律/财务审查。
- 通知默认站内消息；短信、邮件和推送采用事件订阅、去重和失败重试。
- 禁止把开发调试失败、普通状态变化或每次代码提交邮件发给用户；只发送必要且用户订阅的业务通知。
- 任何通知都必须有频率限制、退订或渠道偏好配置。

## 8. 实施顺序

1. 完成身份、组织、角色和审计基础。
2. 完成需求审核、项目和任务拆分。
3. 完成领取、提交、验收、返工和争议。
4. 完成成本记录和贡献毛利报表。
5. 再接支付机构沙箱与真实对账。
6. 小批量真实订单试运行，通过质量与单位经济门槛后再扩张。

当前 SQL 是初始数据结构草案，不代表已部署数据库，也不构成支付、托管或合规能力。
