# 赚钱 APP｜MVP后台与运营工作流设计

> 版本：V0.1 规划稿  
> 定位：居家任务与灵活协作平台。前台只让用户快速找到可做的赚钱任务；复杂的企业管理、任务拆分、质量控制和利润核算全部放在运营后台。

## 1. 本阶段产品判断

当前 GitHub 页面是静态交互原型，不是可真实交易的平台。浏览器本地保存的需求不会发送给运营人员；任务、报酬、领取和提交均为演示数据。不得把原型展示当成真实任务供给或已上线的资金结算能力。

下一步不应继续堆前台页面，而应先把后台业务规则和数据结构设计清楚，再接后端。

## 2. 三类核心角色

| 角色 | 能做什么 | 不应看到什么 |
|---|---|---|
| 任务用户/接单者 | 浏览任务、查看报酬和规则、领取、提交成果、修改、申诉、查看收入状态 | 企业底价、其他人的个人信息、平台利润 |
| 需求方/企业 | 提交需求、确认报价、查看进度、验收或按规则提出修改 | 接单者无关的个人资料、平台内部成本 |
| 平台运营人员 | 审核企业与需求、拆分任务、定价、分派、质检、处理争议、对账 | 超出岗位所需的敏感数据 |

平台管理员另设权限：账号与角色管理、操作审计、费率配置、风险处置。所有后台关键操作必须留痕。

## 3. 两条业务线，不能混账

### A. 平台承包/自营订单

企业把一个完整项目交给平台。平台承担项目组织和整体交付责任，再将项目拆成可独立验收的小任务。

流程：

1. BD录入企业与需求，核验企业主体、联系人、真实业务和付款能力。
2. 运营评估工作量、技能要求、质量标准、物流半径、返工风险。
3. 成本核算：接单者报酬、质检、材料、物流、支付、客服、退款准备。
4. 平台给企业报价并签署适用合同；企业确认订单和交付标准。
5. 运营把项目拆为任务包/工序，设置前置依赖、数量、单价、交付时间和验收规则。
6. 用户领取任务，按模板提交；平台质检，必要时退回有限次数修改。
7. 子任务合格后汇总成项目成果，由平台向企业交付。
8. 按合同和合规支付方案结算；核算该项目贡献毛利。

**利润公式：**项目不含税收入 − 接单者报酬 − 质检/返工 − 材料/物流 − 支付成本 − 退款与坏账准备 = 项目贡献毛利。

平台对企业承担的责任越大，越需要保留项目管理、质量控制和售后成本，不能只看合同价减报酬。

### B. 用户自主发布需求/撮合订单

需求方发布需求，平台负责审核、规范化、报价和撮合。不能让未审核需求直接公开。

流程：

1. 需求方提交标题、用途、成果要求、预算、截止时间和参考资料。
2. 系统先收为“待审核”，不直接公开、不自动承诺接单。
3. 运营审核真实性、合法性、版权/肖像授权、可执行性和预算。
4. 运营补齐交付物、修改次数、验收标准、争议规则。
5. 生成费用明细：接单者报酬、平台服务费、需求方应付总额。
6. 需求方确认后再发布；接单者按展示的报酬接单。
7. 提交、验收、修改、申诉、结算均按规则留痕。

**服务费试算：**原型暂用执行预算的8%作为待验证参数。该费率不是已确定的商业政策，正式上线前必须通过真实客户访谈、订单转化、人工审核成本、支付成本和争议率验证。任何最低服务费、退款扣费或额外费用都必须事先公示。

## 4. 任务状态机

统一任务状态，避免后台和用户端状态不一致：

- 草稿
- 待平台审核
- 待需求方确认报价
- 待发布
- 招募中
- 已接单/进行中
- 待提交
- 待验收
- 待修改
- 复验中
- 已验收
- 待结算
- 已结算
- 争议处理中
- 已取消/已退款

状态迁移必须校验角色权限。例如，接单者不能把任务直接改为“已验收”；企业不能绕过平台规则无限次要求修改；争议中的款项不能显示为接单者可提现收入。

## 5. 任务拆分与质量控制

每个任务至少包含：

- 任务来源：自营承包 / 用户撮合
- 企业/需求方及内部负责人
- 任务标题、说明、交付物格式
- 任务数量、计价单位、接单者报酬
- 预计耗时、技能门槛、是否可手机完成
- 截止时间、可接数量、依赖任务
- 验收清单、允许修改次数、拒收理由
- 素材授权范围、保密要求、数据删除时间
- 物流/材料交接记录（仅适用线下任务）

一个大项目可以拆成多个工序，但每个工序都必须能单独说明“做什么、交什么、怎么验、多少钱”。不得把模糊的“帮忙处理一下”当成任务。

## 6. 真人视频与素材任务的特别规则

平台可允许需求方提出真人实拍素材需求，但必须增加专门审核：

- 说明拍摄者、出镜者、上传者是否为同一人。
- 明确肖像、声音、场景、作品版权及商业使用授权。
- 明确使用渠道、地域、期限、是否允许剪辑/二次创作。
- 禁止未经同意拍摄或上传他人私密空间、敏感个人信息。
- 对未成年人素材设置更严格的监护人授权和审核；不适合的任务直接拒绝。
- 素材文件采用权限控制、下载记录和到期删除策略。
- 涉及广告、医疗、金融等特殊行业内容时，进入人工合规审核。

这类订单的价值不只是“拍一段视频”，而是交付真实、可授权、可追溯的素材。

## 7. 后台模块优先级

### P0：第一版必须具备

1. 企业/需求方档案与人工审核
2. 需求收件箱：待审、通过、退回、拒绝
3. 任务创建、编辑、上下架
4. 自营订单项目拆分与子任务管理
5. 接单者名单、任务分配与进度
6. 提交物查看、验收、退回修改
7. 订单成本表与贡献毛利计算
8. 操作日志、权限控制、异常提醒

### P1：真实试单后再做

1. 用户注册、登录、实名认证（按必要性最小化收集）
2. 文件上传、病毒扫描、对象存储、访问授权
3. 站内通知和必要的短信通知
4. 申诉、争议处理、退款状态
5. 财务对账和合规支付机构接口
6. 企业端订单进度与电子合同

### P2：业务验证后扩展

1. 智能任务拆解建议
2. AI辅助质检与重复内容检测
3. 技能画像和任务推荐
4. 多城市运营、物流批次与线下工序追踪
5. 企业API与批量任务导入

AI只能辅助归类、拆分、检查和提示风险；涉及报酬、拒收、处罚、封禁和争议的决定必须有人复核并可申诉。

## 8. 核心数据实体

建议后端至少设计以下实体，所有表使用唯一ID、创建时间、更新时间和软删除/归档策略：

- users：用户身份、状态、必要的认证引用
- organizations：企业主体、联系人、审核状态
- demand_requests：原始需求、预算、附件引用、审核结果
- projects：平台承包项目、合同价、交付期限、负责人
- tasks：可领取任务、报酬、数量、标准、状态
- task_dependencies：任务之间的前后依赖
- task_assignments：谁在何时领取/被分配了什么
- submissions：提交版本、文件引用、说明、时间
- reviews：验收结果、理由、修改次数、审核人
- orders：订单类型、交易双方、金额与状态
- ledger_entries：应收、应付、平台服务费、退款和调整记录
- disputes：争议原因、证据、处理过程和结论
- audit_logs：后台操作人、操作对象、前后变化和时间
- file_assets：文件归属、权限、授权范围、保留期限

金额统一使用“分”作为整数存储，避免浮点误差；服务费率保存版本和生效时间，不得事后修改已确认订单的费率。

## 9. 资金与结算底线

- 原型阶段不收取真实订单资金，不宣传托管或提现。
- 正式交易前先确定平台法律角色、合同关系、发票和税务处理。
- 资金流与合同流必须一致；使用具备资质的支付机构提供适配的收款、分账和结算产品。
- 不自行形成无资质资金池，不把待验收款项标为可提现。
- 订单页面在付款前展示完整总价、服务费、接单者报酬、退款和争议规则。
- 接单者报酬不得被隐藏扣减；平台不得要求接单押金、垫资刷单或付费培训才能接单。

## 10. MVP验收标准

只有全部满足，才可以从原型进入真实小规模试单：

- 企业和需求来源可核验，不使用虚构任务招募用户。
- 每项任务都有明确交付物、单价、截止时间和验收标准。
- 用户能清楚看到接单报酬和任务状态。
- 需求方能看到服务费和总价，费用在确认前公示。
- 自营订单和撮合订单分账核算。
- 每笔订单可以计算贡献毛利，且把人工、返工、物流和支付成本计入。
- 拒收和修改有理由、有次数上限、有申诉路径。
- 关键后台操作可审计，个人信息按最小必要原则处理。
- 真实资金由合规支付方案处理，退款和对账经过测试。
- 压力、权限、文件上传、异常中断和数据备份测试通过。

## 11. 下一轮开发顺序

1. 把现有静态原型中的“本机演示保存”明确标记，不误导成平台已收到需求。
2. 完成后台信息架构和页面原型：总览、企业、需求审核、项目、任务、验收、财务、风控。
3. 设计API和数据库，不急着接支付。
4. 先接企业档案、需求审核、任务发布和任务状态流转。
5. 用内部测试账号跑通一笔虚拟订单全流程。
6. 找到真实企业和真实需求后，进行人工小批量试单。
7. 根据订单贡献毛利、返工率、审核耗时和复购率决定是否扩张。

**核心原则：前台极简，后台专业；先有真实任务，再扩用户；先算清每单利润，再扩大规模。**
